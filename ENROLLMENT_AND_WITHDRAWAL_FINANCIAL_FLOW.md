# Program — Enrollment & Instructor Withdrawal Financial Flow

## 1. Overview

Program uses a unified financial system that handles:

1. Student course enrollment payments.
2. Manual payment verification by admins.
3. Course enrollment after payment approval.
4. Refunds for rejected enrollment requests.
5. Instructor revenue tracking.
6. Instructor withdrawal requests.
7. Admin verification of instructor withdrawals.
8. Complete financial reconciliation for every instructor.
9. Full transaction and audit logging.

The system must maintain a complete financial history so that **every pound can be traced to a specific financial transaction**.

---

## 2. Core Financial Principle

The dashboard values such as:

- Total Revenue
- On-site Cash
- Withdrawn Cash

should **not be treated as the primary source of truth**.

The primary source of truth should be a **financial ledger / transaction system**.

Dashboard values should be calculated from the underlying financial transactions.

This allows the system to answer:

> Where did every pound come from, where did it go, and why?

---

## 3. Transaction ID Architecture

Every financial operation has a unique transaction ID generated by the Program backend.

There are two different transaction ID concepts.

### 3.1 Program Transaction ID

Generated by the Program backend.

Example:

```text
PRG-TXN-8F42K91M
```

This identifies the transaction inside Program.

It must be:

- Unique
- Immutable
- Generated by the backend
- Never controlled by the frontend
- Never reused

Different financial operations receive different Program transaction IDs.

Examples:

```text
PRG-TXN-000001
PRG-TXN-000002
PRG-WD-000001
PRG-REF-000001
```

---

### 3.2 External Payment Provider Transaction ID

This is the transaction/reference ID provided by the external payment method.

For example:

```text
VF-982734982
```

This may come from:

- Mobile wallet
- InstaPay
- Other supported payment provider

This ID is completely different from the Program transaction ID.

Example:

```text
Program Transaction ID:
PRG-TXN-8F42K91M

Payment Provider:
Vodafone Cash

Provider Transaction ID:
VF-982734982
```

The backend must store both separately.

## 4. Student Enrollment Flow

### 4.1 Starting Enrollment

A student has two ways to start enrollment.

#### Option 1 — Add Course to Cart

```text
Student
    ↓
Adds course to cart
    ↓
Checkout
    ↓
Payment / Enrollment Request
```

#### Option 2 — Direct Enrollment

```text
Student
    ↓
Opens course page
    ↓
Clicks "Enroll"
    ↓
Payment / Enrollment Request
```

Both paths eventually use the same enrollment-request process.

## 10. Admin Enrollment Review

The admin reviews the complete payment information.

The admin should verify:

- Payment screenshot
- Provider transaction ID
- Payer number
- Payment method
- Payment amount
- Course
- Student
- Whether the transaction has already been used
- Whether the student already has an active enrollment
- Whether the payment is legitimate

The screenshot is evidence and should not be treated as the only source of truth.

The backend must prevent the same provider transaction ID from being used for multiple successful enrollments.

---

## 11. Enrollment Approval

If everything is correct:

```text
PENDING
   ↓
APPROVED
   ↓
Create / Activate Enrollment
```

The student receives an in-site notification:

```text
Your enrollment request has been approved.

You are now enrolled in [Course Name].
```

The financial transaction is recorded in the financial ledger.

The instructor's financial share is then reflected in the instructor's financial balance according to the platform's revenue and commission rules.

---

## 12. Enrollment Rejection

If the payment cannot be verified or another problem exists:

```text
PENDING
   ↓
REJECTED
```

The admin must provide a rejection reason.

Example:

```text
The transaction amount does not match the required payment amount.
```

The rejection reason is stored.

The student receives an in-site notification containing:

```text
Your enrollment request for [Course Name] has been rejected.

Reason:
[Rejection Reason]
```

The paid money must then be returned to the student according to the platform's refund process.

The refund must also have its own Program transaction ID.

Example:

```text
Original Payment:
PRG-TXN-000001

Refund:
PRG-REF-000001
```

## 17. Instructor Withdrawal Rule

The instructor does **not** choose the withdrawal amount.

The instructor is forced to withdraw the entire available On-site Cash balance.

Example:

```text
On-site Cash:
13,400 EGP
```

The instructor cannot request:

```text
5,000 EGP ❌
10,000 EGP ❌
12,000 EGP ❌
15,000 EGP ❌
```

The only valid withdrawal amount is:

```text
13,400 EGP
```

The backend must enforce this rule.

The frontend should also display the amount as read-only.

## 22. Expected vs Actual Fees

Expected fees are shown to the instructor before the withdrawal request.

However, the actual fee may differ when the payout is processed.

Therefore, the system should support:

```text
Expected Fee
Actual Fee

Expected Payout
Actual Payout
```

Example:

```text
Expected Fee:
50 EGP

Actual Fee:
50 EGP

Expected Payout:
13,350 EGP

Actual Payout:
13,350 EGP
```

The actual values should be recorded when the admin completes the payout.

## 28. Admin Reconciliation

At the bottom of the instructor financial statement, the system should calculate the current On-site Cash.

Conceptually:

```text
Opening Balance
        +
Instructor Earnings
        -
Refunds
        -
Platform Commission
        +
Financial Adjustments
        -
Completed Withdrawals
        =
Current On-site Cash
```

The system then displays:

```text
Calculated On-site Cash:
13,400 EGP

System On-site Cash:
13,400 EGP

✓ BALANCED
```

The two values must match.

If they do not match:

```text
Calculated On-site Cash:
13,400 EGP

System On-site Cash:
13,100 EGP

⚠ BALANCE DISCREPANCY
```

The admin should not be allowed to complete the withdrawal until the discrepancy is resolved.

## 31. Important Balance Rule

The system should not permanently deduct On-site Cash when a withdrawal request is merely submitted.

Instead, the requested amount should be reserved / placed into a pending withdrawal state.

Example:

```text
On-site Cash:
13,400 EGP

Pending Withdrawal:
13,400 EGP

Withdrawn Cash:
36,600 EGP
```

After successful payout:

```text
On-site Cash:
0 EGP

Pending Withdrawal:
0 EGP

Withdrawn Cash:
50,000 EGP
```

After rejection:

```text
On-site Cash:
13,400 EGP

Pending Withdrawal:
0 EGP

Withdrawn Cash:
36,600 EGP
```

This prevents accounting inconsistencies.

## 32. Unified Financial Ledger

The system should maintain a centralized financial ledger.

Supported transaction types can include:

```text

INSTRUCTOR_WITHDRAWAL
```

Each transaction must have its own Program-generated transaction ID.

## 44. Security and Integrity Rules

### Rule 1 — Backend controls financial values

The frontend must never be trusted for:

- Payment amount
- Withdrawal amount
- Fees
- Instructor balance
- Revenue
- Commission
- Refund amount
- Transaction status

---

### Rule 2 — Program Transaction IDs are backend generated

Never allow users or admins to choose their own Program transaction IDs.

---

### Rule 3 — Provider Transaction IDs must not be reusable

A payment-provider transaction ID that has already been successfully used must not be accepted for another enrollment.

---

### Rule 4 — Withdrawal amount must equal available On-site Cash

The instructor cannot choose a smaller or larger withdrawal amount.

Backend validation must enforce:

```text
withdrawalAmount === availableOnsiteCash
```

---

### Rule 5 — Only one active withdrawal should normally exist

An instructor should not be able to create multiple simultaneous withdrawals against the same balance.

---

### Rule 6 — Withdrawal approval and payout completion are separate concepts

Admin approval means the request is approved.

Actual payout completion should be recorded separately.

Recommended lifecycle:

```text
PENDING
    ↓
APPROVED
    ↓
PROCESSING
    ↓
COMPLETED
```

A rejected request:

```text
PENDING
    ↓
REJECTED
```

---

### Rule 7 — Balance reconciliation is mandatory

Before completing an instructor withdrawal:

```text
Calculated On-site Cash
        =
System On-site Cash
```

If not:

```text
BLOCK WITHDRAWAL
```

## 46. Business-Hours SLA

The student is told:

> The request will be reviewed within 3 hours during official working hours.

Therefore, the system should distinguish between:

```text
Request Created
```

and:

```text
SLA Timer
```

If the request arrives while an admin is active:

```text
Request Created
      ↓
SLA Timer Starts
```

If the request arrives outside official working hours:

```text
Request Created
      ↓
Waiting for next active shift
      ↓
SLA Timer Starts
```

The exact working hours, weekends, and holidays should be defined in the system configuration.

## 47. Final Architecture Principle

The most important architectural principle is:

```text
Financial Ledger
      │
      ├── Student Payments
      ├── Instructor Revenue
      ├── Platform Commission
      ├── Refunds
      ├── Instructor Withdrawals
      └── Adjustments
             │
             ▼
       Financial Balances
             │
             ├── Total Revenue
             ├── On-site Cash
             └── Withdrawn Cash
```

The dashboard is therefore a **view of the ledger**, not the ledger itself.

This guarantees that:

- Every pound is traceable.
- Every payment has a transaction ID.
- Every withdrawal has a transaction ID.
- Every refund has a transaction ID.
- Every instructor balance can be reconciled.
- Admins can see the complete financial history.
- Financial discrepancies can be detected.
- The system can support future accounting features without rebuilding the financial architecture.
